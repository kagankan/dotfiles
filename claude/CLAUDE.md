# CLAUDE.md (user-level)

@CLAUDE.local.md

## 出力ルール

### 調査結果・レビュー結果

- `.ai-output/sessions/` 配下にセッションごとのディレクトリを作り、markdown で書き出す
- セッションディレクトリの取得・作成には `~/.claude/scripts/session-dir.sh` を使用する:
  ```sh
  # スクリプト単体で実行し、出力されたパスを後続コマンドで使う
  ~/.claude/scripts/session-dir.sh "概要"
  ```
  - permission ルールの都合上、`SESSION_DIR=$(...)` のようにコマンド置換で囲まない。スクリプトを単体実行し、出力されたパスを変数に格納して使う
  - `CLAUDE_CODE_SESSION_ID` 環境変数は Claude Code が自動セットするため引数不要
  - 既存ディレクトリがあればそのパスを返し、なければ新規作成する
  - ディレクトリ名の形式: `${作成日}-${CLAUDE_CODE_SESSION_ID}-${概要}`（例: `2026-06-13-abc123-PR レビュー`）
- ファイル名は `${日時}-${日本語タイトル}.md` とする
  - 日時は `date "+%Y-%m-%d-%H-%M"` で取得

### コマンド実行の出力

- `pnpm test` / `pnpm lint` 等の長時間コマンドを実行するときは、出力を必ずファイルに保存する
- 出力先はセッションディレクトリ配下の `logs/` を使う（`/tmp/` は permission の都合で避ける）
  - パス: `.ai-output/sessions/${セッションディレクトリ}/logs/`
  - `.ai-output/` はグローバル gitignore に登録済み
- ファイル名は `$(date +%Y-%m-%d-%H-%M)-<内容>.log` の形式（例: `2026-04-29-02-15-test.log`）
- 結果の確認は保存したファイルを `grep` / `sed` で処理する。同じコマンドを再実行しない
- 例:
  - 実行: `pnpm test --run path/to/file 2>&1 | tee ${SESSION_DIR}/logs/$(date +%Y-%m-%d-%H-%M)-test.log`
  - 確認: `grep -E 'Test Files|Tests |✗|FAIL' ${SESSION_DIR}/logs/2026-04-29-02-15-test.log`
  - 別観点で見直したいときは grep パターンを変えるだけで再実行不要

## Git のルール

### commit --amend

- **`git commit --amend` の前に必ず `git log -1 --stat` で直前のコミットを確認する。** ユーザーから amend の指示があった場合も例外なく確認する
- 確認するのは「直前のコミットが、今 amend しようとしている変更と同じまとまりか」。以下のいずれかに当てはまるなら amend せず、通常のコミットにするかユーザーに確認する
  - 自分が今のセッションで作ったコミットではない
  - 指示を受けた時点より後に別のコミットが積まれている
  - コミットメッセージや変更ファイルが、今の変更と無関係
- amend の指示はその時点の HEAD に対するもので、その後に別のコミットを積んだ場合は無効になる（無関係なコミットに変更を混ぜ込む事故が起きるため）

### コミットメッセージ

- 「レビュー指摘に対応」「指摘を反映」のようなメッセージを使わない。何をしたか・なぜを書く
- コミットメッセージは diff の内容を説明するものであり、作業の経緯（誰に言われたか、どのフェーズで気づいたか）を記録するものではない
- conventional commits の type の使い分け:
  - `feat` — ユーザーから見える新機能の追加
  - `fix` — プロダクションコードのバグ修正。テストの修正には使わない
  - `refactor` — 外部から見た振る舞いを変えないコードの構造変更（リネーム、関数の分割・統合、責務の移動等）
  - `perf` — パフォーマンス改善を目的としたコード変更
  - `test` — テストの追加・修正・リファクタリング。プロダクションコードの変更を含まない場合に使う
  - `docs` — ドキュメント（README、JSDoc、コメント等）のみの変更
  - `style` — コードの意味に影響しないフォーマット変更（空白、セミコロン、prettier 適用等）
  - `build` — ビルドシステムや外部依存の変更（webpack/vite 設定、package.json の依存更新等）
  - `ci` — CI 設定ファイルやスクリプトの変更（GitHub Actions、CircleCI 等）
  - `chore` — 上記のいずれにも当てはまらない雑務（`.gitignore` の更新、開発ツールの設定変更等）
  - `revert` — 過去のコミットの取り消し

## Pull Request のルール

- PR は必ず **Draft** 状態で作成する。Open に切り替えるのは人間が行う
  - `gh pr create` を使う場合は `--draft` フラグを必ず付ける
  - 既存 PR を作り直す場合も Draft で作成する
- PR description は、リポジトリに `.github/pull_request_template.md` がある場合は**そのテンプレートのセクション構成をそのまま使って**記入する
  - `## Summary` / `## Test plan` 等の独自構成に書き換えない
  - テンプレートのコメント (`<!-- ... -->`) は埋めるかコメントごと差し替える
  - 既存のチェックリスト項目は AI 側で完了確認したものだけ `[x]`、人間が後でやる項目（セルフレビュー、AI レビュー、ラベル付与、Slack 連絡等）は `[ ]` のまま残す
  - テンプレートが無いリポジトリのみ Summary / Test plan で書く
- 書く必要のない項目は削除し、常体で簡潔に書く
- 検証用 PR（マージしない前提）のタイトルには先頭に `【マージしない】` を付ける

## PR の書き方

### 全体

- タイトルは PR 全体を包括する内容にする。複数コミットにまたがる場合、最後に積んだコミットの内容だけを反映したタイトルにしない
- 事実だけ書く。実行していない検証を「確認済み」と書かない。未対応・積み残しがあるなら隠さず 1 行で書く
- 用語はコード上の識別子（コンポーネント名・関数名・パス）に揃える。レビュアーが本文の語から diff の該当箇所を検索できるようにするため

### 概要（背景・目的）

- base ブランチに対する diff の内容だけを書く。実装過程での中間的な判断や、base に存在しない問題への言及は含めない
- 「〜にしました」「〜を削除しました」のようにコミットの変遷（実装過程でどう変わったか）を語る書き方はしない。base との diff が表す「今の状態」を直接説明する。設計理由を書きたい場合も「なぜ削除したか」ではなく「なぜこの設計にしているか」（例:「toast は引数から削除しました」ではなく「toast は呼び出し元によらず同じ挙動のため hook 内部で呼んでいる」）という、現状を主語にした書き方にする
- **PR がまだ Open していない（レビュアーがまだ読んでいない）段階では、その中間の開発過程は誰にも見えていない。** レビュアーが見るのは base ブランチに対する最終的な diff だけであり、「途中で見つけたバグを直した」「セルフレビューで気づいて直した」というような開発過程を示す見出し・段落を独立させて作らない（「〜にしました」という文レベルの話だけでなく、見出し・トピックの立て方自体にも適用される）。そのような修正内容は、対応する意味的なまとまり（例: バリデーション周りの修正なら「バリデーションを集約」のトピック）に溶け込ませ、最終的な挙動として説明する

### 実装内容

- **実装内容は diff の代わりではなく、diff を読むためのガイド**。書くのは「何をしたか（どこを見ればいいか）」と「なぜそうする必要があったか」の 2 つだけ
- **diff を見れば分かることは書かない。** 以下は原則として省く
  - 変更したファイル名・関数名の羅列
  - コードを読めば分かる実装の詳細（`optional chain` で受ける、引数を 1 つ増やした、条件分岐を early return にした等）
  - リネーム・型定義の追加・import の整理といった機械的な変更
  - 挙動が変わらない項目を 1 つずつ列挙すること。「挙動は変わらない」と 1 行書けば足りる
- **なぜ必要かは、diff から読み取れないときだけ書く。** 制約（hook は条件付きで呼べない、server が型に反した値を返す等）や仕様上の要請がそれにあたる。コードを見れば自明な理由は書かない
- `- **(意味的なまとまり)**` を親項目にして `  - (実装の詳細)` をぶら下げる階層構造にする。長文の散文にしない
  - 親項目は「変更の意味的なまとまり」であってファイル単位・コミット単位ではない
  - 親項目は 3〜5 個程度、ぶら下げる詳細は 1 トピックにつき多くても 3 個まで。それを超えるなら、粒度が細かすぎるか PR が大きすぎる
- **チャットの中で検討してやめた案は書かない。** レビュアーが見るのは最終的な diff だけで、採用しなかった案は存在しない
  - 例外は「レビュアーが同じ疑問を持つと予想でき、かつ却下の理由が diff から読み取れない」場合のみ。そのときも「なぜこの設計か」の形で 1〜2 行に収め、検討の経緯としては書かない
- 挙動が変わる箇所は、変わることが分かる粒度で書く。挙動の変化はレビュアーが diff から見落としやすいため、ここだけは省略しない

### レビュアーに特に見てほしい点

- 本当に重要なこと（判断に迷った箇所、大きめのリファクタなら「挙動が変わっていないことの確認」等）だけに絞る。多くても 2〜3 点
- 個々の設計判断の説明はここに書かず「実装内容」に書く

### 確認項目（動作確認リスト・QA 項目）

- 確認項目のチェックリストで、Swagger UI 等の API ドキュメントへの直リンクが使える場合、対象エンドポイントごとに直リンクをその確認項目の直上に置く。複数エンドポイントの直リンクをまとめて先頭に列挙し、チェックリストを別ブロックにして後ろにまとめるのはしない（並び: URL → 空行 → その URL に対応する `- [ ]` 群 → 空行 → 次の URL、の繰り返し）。QA 担当者が該当エンドポイントを手動で探す手間を省くため

### 本文の編集時のルール

- **PR 本文を編集するときは、必ず直前に `gh pr view --json body` で現在の body を取得し直し、それをベースに編集して書き込む。** 手元に保存した過去のコピー（scratchpad のファイル等）からの上書きは、ユーザーが手動で加えた編集を消してしまうため絶対にしない

## GitHub へのコメント投稿のルール

- Claude が `gh` コマンド等で GitHub に直接コメントを投稿する場合（PR コメント、レビューコメント、issue コメント、PR レビューの本文すべて）、人間の発言と区別できるよう、本文の冒頭に以下の署名を必ず付ける

  ```markdown
  🤖 Claude による自動投稿
  ```

- 署名は本文の 1 行目に置き、空行を 1 つ空けてから本文を続ける
- 対象は「Claude が投稿主体になるもの」に限る。PR 本文（description）やコミットメッセージのように、ユーザーの成果物として扱われるものには付けない

## 技術的な選択肢を検討・提示するときのルール

- 複数の技術的選択肢を検討するときは、すぐに結論へ飛ばず、まず評価の観点（軸）を広げて洗い出してから比較する
- ユーザーに選択を委ねるときは、各選択肢の**メリット・デメリットを必ず併記する**
- 補足情報として、どの選択肢が一般的か（著名な OSS や有名プロジェクトでの採用例など）が分かれば添える
- **命名の提案**にも同じルールを適用する。変数名・関数名・ファイル名等の候補を出すときは、複数案とそれぞれのメリット・デメリットを示す。1 つだけ出して「これでいいですか？」と聞かない

## 日本語の表記ルール

日本語を囲む括弧は全角を使用する（例: `（超過時に〜と表示）`）。コード中のコメントや tsdoc にも適用する。

## lint ルールの追加・アップデート時に出現した新たなエラーへの対応方針

- コード動作に影響を与えるような変更は行わない。つまり、コメントの追加・削除のみ行う
- そのブランチ内での対応が難しいものは、該当行に `eslint-disable` で打ち消す（ルールを off にはしない）

## コメントに関するルール

- 既存のコメントを勝手に削除しない。リファクタリングや書き換え時も、明らかに obsolete でない限りそのまま残す
- **ファイルの移行・統合・書き換え時も、元ファイルにあったコメントを新ファイルに引き継ぐ**。設定ファイルの移行（例: webpack → vite）でも、元のコメントが説明している背景や意図がまだ有効なら必ず移植する
- 削除はユーザーから明示的に指示があった場合のみ行う
- 新規コメントの追加は最小限にとどめる（WHY が非自明な場合のみ）
- JSDoc / tsdoc は目的・概要だけ示す。実装の詳細（条件分岐の網羅、内部ステップの列挙等）は書かない。詳細な補足が必要な場合は該当コードの近くにインラインコメントで書く

## テストの書き方・レビュー

### テスト名は振る舞いを事実として記述する

- テスト名にメソッド名・戻り値の型など実装の詳細を含めない
- `{メソッド名}_{事前条件}_{想定する結果}` のような形式は使わない
- 非開発者でも読める言葉で、システムの振る舞いを断定形で書く
  - Bad: `IsDeliveryValid_InvalidDate_ReturnsFalse`
  - Bad: `過去の日付が指定された配達は不正とすべきである`（希望・要望の表現）
  - Good: `過去の日付が指定された配達は不正である`（事実の記述）
- ただし内部 utility（API クライアント、パーサー等）のテストでは、対象の技術要素（Web API 名、プロトコル名、データ形式等）をテスト名に含めるほうが効率的な場合がある。このルールはユーザー向けの振る舞いを検証するテストに主に適用する

### 自作自演テストを書かない

- テストの期待値をプロダクトコードと同じ計算式で導出しない。期待値は具体的なリテラル値で書く
  - Bad: `expect(tax(price)).toBe(price * 0.1)`（プロダクトコードと同じロジックを再現しており、丸め処理のバグを検出できない）
  - Good: `expect(tax(1050)).toBe(105)`
- テストコードがプロダクトコードのロジックを複製している場合、バグがあっても同じバグが期待値に反映されてテストが通ってしまう（偽陰性）
- レビュー時は「期待値の根拠がプロダクトコードと独立しているか」を確認する
